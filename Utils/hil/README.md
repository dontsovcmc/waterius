# Стенд: автоматические тесты на живом железе

Прогоняет блоки D, E, F, G, H, I из [docs/manual-test-plan.md](../../docs/manual-test-plan.md)
без человека. То, что человек делал руками — «выключите роутер», «укажите
несуществующий брокер», «спустите унитаз», — делают плата-манипулятор и
управляемая точка доступа.

## Из чего собран

| Часть | Что делает | Как подключена |
|---|---|---|
| **METF** (ESP32-C6 Super Mini) | Кнопка, входы счётчиков, сброс, чтение UART Ватериуса | HTTP, `metf_python_client` |
| **WT32-ETH01** с [esp32_nat_router](https://github.com/martin-ger/esp32_nat_router) | Точка доступа: включить, погасить, переименовать, сменить канал, зарезать трафик | Консоль по TCP, порт 2323, через Ethernet |
| Приёмник HTTP | Ловит посылки и **присылает настройки в ответе** | `receiver.py`, поток в процессе pytest |
| [amqtt](https://github.com/Yakifo/amqtt) | Брокер на время прогона | поднимается фикстурой в самом процессе pytest |
| **NodeMCU** с [AT-прошивкой](nodemcu-at.md) | HTTP-клиент внутри сети портала Ватериуса | USB, AT-команды |

Распиновка METF — из `Utils/waterius2_factory_test/main.py`: кнопка `GPIO1`,
вход 1 `GPIO2`, вход 0 `GPIO3`, сброс `GPIO0`, UART Ватериуса на `Serial0`.

Аплинк у WT32-ETH01 проводной, и это не прихоть. Во-первых, при аплинке по Wi-Fi
радио одно, точка доступа обязана жить на канале роутера, и `set_ap_channel` в
такой сборке просто отсутствует. Во-вторых, стенд гасит Wi-Fi командой
`ap disable` — управление обязано идти по проводу, иначе команда отрубит саму
себя.

Как ввести плату в строй с нуля — [wt32-eth01.md](wt32-eth01.md): прошивка,
аплинк, удалённая консоль, настройка и приёмка. Известная ошибка её прошивки,
из-за которой клиенты точки теряют выход наружу, — [router-nat-bug.md](router-nat-bug.md);
стенд обходит её перезагрузкой платы, исправление в апстрим ещё не отправлено.

NodeMCU нужен для портала: в режиме настройки Ватериус поднимает свою точку
доступа, и попасть в неё больше некому — рабочая машина занята своим радио, а
точка стенда в сборке с проводным аплинком присоединяться к чужим не умеет.
Прошивка и команды — [nodemcu-at.md](nodemcu-at.md).

## Запуск

```bash
pip install -r requirements.txt
cp stand.ini.example stand.ini      # адреса, пины, MAC Ватериуса

python router.py --host <ip> show config   # проверка связи с роутером

cd ../..                            # в корень репозитория
python3 -m pytest Utils/hil -q                    # только разбор лога, без железа
python3 -m pytest Utils/hil --stand -m "not slow" # быстрые тесты на стенде
python3 -m pytest Utils/hil --stand -k E1 -v      # один тест по номеру из плана
python3 -m pytest Utils/hil --stand -m portal -v  # портал: файлы образа и API
python3 -m pytest Utils/hil --stand               # всё, включая часовые
```

Без `--stand` тесты железа пропускаются, а разбор лога проверяется где угодно —
он не требует ни pyserial, ни paho-mqtt.

## Как устроен тест

```python
def test_E1_flow_alarm(stand, quiet):
    stand.setup_alarms(channel=1, factor=10, alarm_flow=3600, ctype=NAMUR)
    stand.reset_observers()
    stand.dut.pulses(channel=1, count=2, gap=3.0)

    session = stand.wait_session(timeout=120, mode=ALARM_MODE)
    session.assert_alarm(flow1=1, flow0=0)
```

Три вещи, которые делают это возможным.

**Настройки приезжают в ответе приёмника.** Тело ответа 200 прошивка копирует в
`json_settings`, применяет и тут же отправляет данные повторно. Значит любой
параметр — пороги, вес импульса, период, маска квитанции — ставится из теста без
портала и без брокера. `stand.setup()` дополнительно проверяет, что настройка
действительно применилась: строкой `Apply setting:` в логе и новым значением во
второй посылке.

**Сеанс — один объект.** `wait_session()` сводит лог, посылку и сообщения
брокера. Это важнее, чем кажется: блоки отправки печатаются дважды за сеанс,
а `HTTP: Send OK` одинаков для облака и своего сервера, так что поиск строки по
всему буферу рано или поздно поймает не ту.

**Сеть — контекстные менеджеры.** `stand.net.ap_off()` — сети нет вовсе;
`internet_down()` — сеть есть, трафика нет; `cloud_down()` и `mqtt_down()` —
недоступен один получатель. Последние два не воспроизвести ничем, кроме правил
фильтра, а без них не проверить маску квитанции.

## Портал

Отдельный блок тестов (`test_portal.py`, метка `portal`). Стенд удерживает
кнопку, Ватериус поднимает свою точку доступа, и AT-плата - единственный, кто
может в неё зайти, - обходит все адреса портала.

Проверяются три вещи, и каждая ловит свою поломку: страница отдаётся целиком
(образ LittleFS почти полон, и переполнение видно как обрезанный файл, а не как
ошибка сборки); статика совпадает с `ESP8266/data` байт в байт (прошивка и
файловая система шьются разными командами, и залитый по ошибке старый образ
ничем больше не виден); в html не осталось `%PLACEHOLDER%`. Плюс `/api/*` -
разбираемый JSON, и `/api/status/N` без поля `error`, то есть i2c с attiny жив.

Побайтная сверка идёт, только когда версия в устройстве совпадает с версией в
дереве, - иначе тест пропускается с явным текстом. Прошивка и её засады -
[nodemcu-at.md](nodemcu-at.md).

## Брокер

Брокер поднимается фикстурой в самом процессе pytest (`broker.py`, пакет
`amqtt`) — внешний mosquitto не нужен: его ставят руками, на каждой машине
по-своему, и его отсутствие превращало весь блок MQTT в молчаливый пропуск.
Хранилище выключено: переживёт ли удерживаемое сообщение перезапуск брокера —
вопрос к брокеру, а не к прошивке.

Две вещи, на которых легко получить ложный результат.

**Флаг retain в живой доставке всегда нулевой.** Брокер выставляет его только
тому, кто подписался уже после публикации (MQTT 3.1.1, 3.3.1.3), поэтому
`test_I7` смотрит не на подписчика стенда, а на то, что видит новый —
`MqttWatch.fetch_retained`.

**У amqtt есть дефект, из-за которого стенд менял бы поведение устройства.**
При подключении клиента брокер рассылает ему удерживаемые сообщения по всем
фильтрам, какие зарегистрировал хоть кто-нибудь, а не по его собственным
(`amqtt/broker.py`, цикл `for topic in self._subscriptions` в обработчике
подключения). Ватериус на каждое полученное сообщение публикует пустое с
флагом retain (`ha/subscribe.cpp`, `clear_retained`), то есть из-за подписки
стенда на `#` он вычистил бы retain у собственных показаний и у автодискавери.
`broker.py` накладывает заплату наследником, а `test_broker.py` держит её под
тестом; исправление в апстрим ещё не отправлено.

## Что стенд не проверяет

Отрисовку страниц портала и мастер настройки (нужен браузер; страницы и API -
см. выше), captive portal на телефоне, OTA, физическую воду, тип входа
«Электронный (+)» (нужен источник уровня, а не сухой контакт) и **число вспышек
светодиода**.

Про вспышки отдельно: код в лог не печатается, а опрос пина по HTTP слишком
медленный, чтобы поймать вспышку в 200 мс. Поэтому тесты G3–G5 проверяют не код,
а причину, из которой он считается. Настоящий подсчёт появится, когда в METF
будет счётчик фронтов на прерываниях, а светодиод будет припаян к плате.

Всё перечисленное остаётся в ручном плане.

## Прошивка METF

Плата стенда — ESP32-C6 SuperMini с прошивкой из `/Users/dontsov/CODE/metf`.

```bash
ls /dev/cu.*      # порт определять каждый раз: C6 виден как usbmodem*
~/.platformio/penv/bin/pio run -d <metf> -e esp32-c6-super-mini -t upload \
  --upload-port /dev/cu.usbmodemXXXX
```

**Сеть платы выбирается при сборке, а не при запуске.** Имя и пароль точки
компилируются внутрь прошивки из `secrets.ini` (файл не коммитится) флагами
`SSID_NAME`/`SSID_PASS`. Прошивка с другими кредами уводит плату в другую сеть и
на другой адрес, и стенд, который ищет её по `host` из `stand.ini`, просто
перестаёт получать ответы — без единой ошибки, по таймауту. Поэтому перед каждой
заливкой сверяйтесь с `secrets.ini`: на плату попадёт то, что лежит в файле, а
не то, что на ней стоит сейчас. Свой адрес плата печатает в USB-консоль (115200)
при старте, там же видно, к какой сети она подключается.

## Прошивка Ватериуса на стенде

Модель платы определяет окружение: `"model":2` в посылке (или 4 МБ флеша) —
это `waterius_2`, `esp01_1m` — классика на 1 МБ. Залить не то окружение можно
незаметно: собирается и шьётся всё одинаково.

```bash
~/.platformio/penv/bin/pio run -d ESP8266 -e waterius_2               # прошивка
~/.platformio/penv/bin/pio run -d ESP8266 -e waterius_2 -t buildfs    # образ статики
esptool --port <порт> --baud 115200 --connect-attempts 0 write-flash \
  0x0        ESP8266/.pio/build/waterius_2/firmware.bin \
  0x300000   ESP8266/.pio/build/waterius_2/littlefs.bin
```

Оба образа — **одним вызовом** `esptool`: между записями чип остаётся в
загрузчике. Разбив на две команды, вторую придётся ловить заново (`CLAUDE.md`,
«GOTCHA»), а забыв — получить рассогласованную пару, о которой ниже.

**Питание ЕСП даёт attiny, и только на сеанс.** Короткое нажатие — две минуты
(`WAIT_ESP_MSEC`), длинное — десять (`SETUP_TIME_MSEC`). Поэтому `esptool`
запускают с `--connect-attempts 0` и жмут кнопку: он ждёт появления питания сам.
Пока ЕСП сидит в загрузчике, она не говорит attiny «сплю», и окно выбирается
целиком. Запись первых 658 КБ с нуля не трогает ни настройки (они в EEPROM выше
образа), ни файловую систему.

**Прошивка без файловой системы выглядит здоровой.** Устройство отвечает
правильной версией в логе, страницы открываются, а статика на нём — от прошлого
выпуска. Стенд это ловит: `P1` падает на новой странице (`/alarms.html: 404`),
`P3` — на всех файлах сразу («14248 байт против 15250 в образе»).

**Программатор перед прогоном отключайте.** Оставленный на плате USB-TTL держит
ЕСП в загрузчике: `esptool` подключается мгновенно и печатает `Stub flasher is
already running`, а лог пуст — METF не получает ни строки, кнопка ничего не
даёт, и стенд видит мёртвое устройство. Линия сброса до платы при этом не
доходит, так что `esptool ... run` не помогает: выйти из загрузчика можно только
снятием питания.

## Чего не хватает в METF

**Серия импульсов задаётся с компьютера.** На каждый фронт наматывается сетевая
задержка, а тесты тревог сравнивают интервалы с порогом. `dut.py` уже умеет
звать `/pulse` (выдержка на плате) и откатывается на два запроса, если метода в
клиенте нет; для ритмичных серий нужен `/pulse_train` на самой плате.

**Проверка потерь требует METF 5 и клиента 0.4** (опубликован на PyPI, в
`requirements.txt` затребован). Кольцо лога платы расширено до
64 КБ (511 строк по 128 символов — полный сеанс Ватериуса занимает 193), а
вытесненные строки считаются и отдаются в `GET /read/stat`. `LogWatcher` снимает
счётчик по краям каждого ожидания и валит тест, если за это время кольцо
что-нибудь выбросило: молчаливая потеря делает ложно-зелёным и «сеанс пришёл», и
«сеанса не было». Если плата всё же окажется с прошивкой младше 5 (`/read/stat`
подхватит обработчик `/read`) или клиент - старый, проверка выключается с
предупреждением в лог, а прогон идёт как раньше: обновление платы не должно быть
условием запуска.
