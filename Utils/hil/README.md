# Стенд: автоматические тесты на живом железе

Прогоняет блоки A, B, C, D, E, F, G, H, I, J, K из
[docs/manual-test-plan.md](../../docs/manual-test-plan.md) без человека. То, что
человек делал руками — «выключите роутер», «укажите несуществующий брокер»,
«спустите унитаз», «дождитесь, пока портал закроется», — делают
плата-манипулятор, управляемая точка доступа и приёмник, который умеет
отвечать не только двумястами.

Чего стенд не может в принципе — [04_not-tested.md](04_not-tested.md); что из
плана он уже закрыл — таблица в начале самого плана.

## Из чего собран

| Часть | Что делает | Как подключена |
|---|---|---|
| **METF** (ESP32-C6 Super Mini) | Кнопка, входы счётчиков, сброс платы, чтение UART Ватериуса | HTTP, `metf_python_client` с повторами (`metf.py`) |
| **WT32-ETH01** с [esp32_nat_router](https://github.com/martin-ger/esp32_nat_router) | Точка доступа: включить, погасить, переименовать, сменить канал, зарезать трафик | Консоль по TCP, порт 2323, через Ethernet |
| Приёмник HTTP | Ловит посылки и **присылает настройки в ответе** | `receiver.py`, поток в процессе pytest |
| [amqtt](https://github.com/Yakifo/amqtt) | Брокер на время прогона | поднимается фикстурой в самом процессе pytest |
| **NodeMCU** с [AT-прошивкой](02_nodemcu-at.md) | HTTP-клиент внутри сети портала Ватериуса | USB, AT-команды |

Распиновка METF — из `Utils/waterius2_factory_test/main.py`: кнопка `GPIO1`,
вход 1 `GPIO2`, вход 0 `GPIO3`, сброс `GPIO0`, UART Ватериуса на `Serial0`.

Линия сброса заведена на вывод reset у attiny и перезагружает **всю плату**, а
не одну ЕСП: после импульса счётчик сбросов attiny в посылке растёт, а ЕСП
сообщает `esp restarted: 0` — для неё это обычное включение. Уронить одну ЕСП,
оставив attiny на ходу, линией нельзя; это делает выход из режима настройки
(`/api/turnoff` → `ESP.restart()`), на нём и стоит `test_H7`.

Аплинк у WT32-ETH01 проводной, и это не прихоть. Во-первых, при аплинке по Wi-Fi
радио одно, точка доступа обязана жить на канале роутера, и `set_ap_channel` в
такой сборке просто отсутствует. Во-вторых, стенд гасит Wi-Fi командой
`ap disable` — управление обязано идти по проводу, иначе команда отрубит саму
себя.

Как ввести плату в строй с нуля — [01_wt32-eth01.md](01_wt32-eth01.md): прошивка,
аплинк, удалённая консоль, настройка и приёмка. Известная ошибка её прошивки,
из-за которой клиенты точки теряют выход наружу, — [03_router-nat-bug.md](03_router-nat-bug.md);
почему перекрывающиеся каналы рвут посылки на середине —
[05_air-and-loss.md](05_air-and-loss.md);
стенд обходит её перезагрузкой платы, исправление в апстрим ещё не отправлено.

NodeMCU нужен для портала: в режиме настройки Ватериус поднимает свою точку
доступа, и попасть в неё больше некому — рабочая машина занята своим радио, а
точка стенда в сборке с проводным аплинком присоединяться к чужим не умеет.
Прошивка и команды — [02_nodemcu-at.md](02_nodemcu-at.md).

## Запуск

```bash
pip install -r requirements.txt
cp stand.ini.example stand.ini      # адреса, пины, MAC Ватериуса

python router.py --host <ip> show config   # проверка связи с роутером

cd ../..                            # в корень репозитория
python3 -m pytest Utils/hil/selftest -q            # сам стенд, без железа
python3 -m pytest Utils/hil --stand -m "not slow" # быстрые тесты на стенде
python3 -m pytest Utils/hil --stand -k E1 -v      # один тест по номеру из плана
python3 -m pytest Utils/hil --stand -m portal -v  # портал: файлы образа и API
python3 -m pytest Utils/hil --stand               # всё, включая часовые
python3 -m pytest Utils/hil --stand --durations=0 # то же, со сводкой времени по фазам в конце
python3 -m pytest Utils/hil --stand --pcap -k G4  # с дампом трафика к упавшим
python3 -m pytest Utils/hil --stand --experimental # и экспериментальные функции
python3 -m pytest Utils/hil/selftest -q --reverse  # набор задом наперёд: ловит зависимость по порядку
python3 -m pytest Utils/hil --stand --soak -k Z1   # длинный прогон, по умолчанию --soak-minutes=60
```

Без `--stand` тесты железа пропускаются, а `selftest/` проверяется где угодно —
он не требует ни pyserial, ни paho-mqtt.

**Лог пишется сам, всегда.** Каждый прогон заводит
`Utils/hil/logs/hil-<дата>.log` и печатает его путь в заголовке сессии. Ни `tee`,
ни `-u` не нужны: файл строчный, поэтому оборванный прогон сохраняет всё, что
успел напечатать. В файле три источника сразу - вывод pytest (строки тестов,
сводка, traceback), loguru самого стенда и стандартный logging клиента METF.

```bash
pytest Utils/hil --stand                          # лог сам, в Utils/hil/logs/
pytest Utils/hil --stand --stand-log=/tmp/run.log # свой путь
pytest Utils/hil --stand --stand-log=off          # без файла
```

Зачем это по умолчанию: прогон стенда идёт часами, и без файла нельзя ни
посмотреть, что он делает сейчас, ни разобрать, на чём он умер. Цена известна -
прогон шёл 7,5 часов вместо трёх, потому что на середине отвалился METF, а
увидеть это было нельзя: вывод уходил в `tail`, и в конце в буфере остался один
traceback, все результаты тестов пропали.

Время печатается по ходу прогона: под каждым тестом — его время вместе с
подготовкой и возвратом стенда, после последнего теста файла — сумма по файлу.

**Если поведение не сходится с исходником — сначала снесите `__pycache__`.**
Python считает `.pyc` свежим, когда совпали два поля его заголовка: время
правки исходника в секундах и его размер. Правка `ATTEMPTS = 1` на
`ATTEMPTS = 3` размера не меняет, и если она попала в ту же секунду, что и
предыдущий запуск, старый байткод будет выполняться сколько угодно долго. Так
повторы METF молча не работали два прогона подряд: в файле стояло 3, в логе
печаталось «попытка 1 из 1», и заметил это только селф-тест.

```bash
find Utils/hil -name __pycache__ -type d -exec rm -rf {} +
```

`stand.ini` не из соседней папки передавайте одним аргументом:
`--stand-config=<путь>`. Через пробел pytest примет путь за тесты и загрузит
чужой `conftest.py`.

### Эфир: канал и полоса

Эфир решает судьбу прогона: оборванные тела посылок и провалы чтения лога
рождаются в нём, а выглядят дефектом прошивки (05_air-and-loss.md). Поэтому
канал точки стенда - не «как осталось с прошлого раза», а настройка:

| Настройка `stand.ini` | Аргумент | Что значит |
|---|---|---|
| `[router] ap_channel` | `--ap-channel` | канал точки стенда; ставится при подъёме |
| `[router] ap_channel_other` | `--ap-channel-other` | куда уводят точку тесты смены канала (W4, W5) |
| `[router] ap_bandwidth` | `--ap-bandwidth` | какой полосой точка обязана вещать |

Канал держите дальше пяти от домашней сети, в которой сидят Мак с приёмником и
METF: частичное перекрытие хуже общего канала. Полосу стенд не переключает - в
консоли роутера такой команды нет, - а сверяет со сканом эфира и говорит о
расхождении до первого теста (`air.py:check`).

Перед каждым файлом тестов в лог пишется строка с уровнями сигнала обеих плат
(`conftest.py:_log_air`): задним числом эти числа взять неоткуда, а без них
отказ «посылка не пришла» не отличить от «эфир съел сегмент».

METF отвечает по Wi-Fi, а тесты тот же эфир намеренно ломают: гасят точку
доступа, меняют канал, поднимают точку самого Ватериуса. Поэтому вызовы к плате
идут через `metf.py`: короткая осечка связи - повтор (три попытки с удвоением
паузы, каждая видна в логе), а молчание дольше минуты останавливает весь прогон
с одной внятной строкой. Повторяется только отказ соединения: `ReadTimeout`
значит, что запрос дошёл, а ответа нет, и для `/pulse` повтор нажал бы кнопку
второй раз - за длинным нажатием это режим настройки вместо передачи. Раньше отлучка METF давала час одинаковых traceback:
23 упавших теста подряд, ни один из которых до прошивки не дошёл.

**Перезагрузку платы стенд замечает сам.** С одиннадцатого протокола METF
ставит на каждый ответ заголовок `X-Uptime-Ms` - миллисекунды со своего старта.
Клиент хранит последнее число (`metf.py:Metf._note_uptime`), и уменьшение
считает перезагрузкой: отличить её от занятости больше нечем, а последствия
заметные - кольцо лога пусто, сервер времени выключен, выводы вернулись во
вход. Прогон при этом не прерывается: тест вполне может пройти. Но если он
упал, к отказу приписывается «во время теста METF перезагружалась», а в конце
прогона печатается список таких тестов - чтобы беду стенда не записали на счёт
прошивки Ватериуса. Плата младше одиннадцатого протокола - предупреждение на
старте, не отказ.

**Чтение лога подтверждается.** Прежде `GET /read` осушал кольцо в момент сборки
ответа: строки существовали в одном экземпляре, и не доехавший ответ уносил их
навсегда. Повтор приносил уже следующие, дыра выходила молчаливой, и падал потом
не тот тест и не там - 24 сентября 2026 это выглядело как «сеанс не пришёл за
300 с» при живом сеансе, из которого пропала первая строка. За один прогон так
умерло девять тестов из двенадцати упавших.

С протокола 12 плата держит отданное, пока стенд не назовёт номер последней
полученной строки: он приходит заголовком `X-Log-Seq`, а возвращается
параметром `ack` на следующем чтении - **лишних запросов при этом ноль**.
Потерянный ответ теперь ничего не стоит: тот же запрос отдаёт то же окно,
поэтому чтение повторяется по любому сетевому отказу (`metf.py:serial_read`).

Подтвердить доставку самим ответом `200` нельзя: он уходит **после** отправки и
сам может не дойти. Подтверждения на уровне TCP тоже мало - из 81 оборванного
чтения в прогоне 24 сентября 23 были таймаутом чтения, где ответ мог и доехать,
но позже, чем клиент сдался; плата сочла бы его доставленным и забыла строки.
Подтверждает тот, у кого строки в руках.

Прошивка младше двенадцатой к прогону не допускается (`metf.py:check`, отказ
`MetfTooOld`): держать второй путь чтения лога дороже, чем прошить плату.

До первого теста стенд проверяет все платы и пишет в лог по строке на каждую:
`стенд: METF … - есть, протокол 10, сеть «…», -68 дБм, обрывы: none`,
`стенд: WT32-ETH01 … - есть`, `стенд: AT-плата … - есть`,
`стенд: Ватериус - есть: attiny …, ЕСП …`. Любой отказ - сразу с именем платы.
METF досматривается подробнее прочих (`metf.py:check`): версия протокола, в
какой она сети, с каким запасом сигнала и не она ли сама сидит на точке стенда -
см. «Прошивка METF». Ватериус проверяется нажатием кнопки, и за две секунды стартовый лог
различает три поломки: на UART ни строки (кнопка не доходит, нет питания,
программатор на UART); ЕСП жива, но `Attiny not found.` (attiny не отвечает по
i2c - прошивка или фьюзы); строки идут, а сеанс не начинается. К любому отказу
приложено всё, что METF прочитала после нажатия, байт в байт - вместе с
недописанной строкой, которой в разобранном логе нет.

Флаг `--experimental` включает тесты функций, поведение которых ещё может
измениться. Сейчас это много воды сразу (`E1`, `E2`) и протечка по квантам
тишины (`E3`). Без флага они пропускаются: падение такого теста ничего
не говорит о прошивке, пока не решено, как функция должна работать. Датчик
протечки, режим отпуска и остановка потребления под флаг не попадают и идут
всегда: их правила устоялись.

Не путать с пользовательской пометкой: в [Alarms.md](../../Alarms.md) и в
портале экспериментальными названы все четыре тревоги целиком. Здесь флаг
решает у́же — какие тесты гонять по умолчанию.

Флаг `--soak` включает многочасовой прогон (`test_soak.py`): плановые сеансы
раз в пять минут, без пропусков, без сбоев i2c и с растущим счётом. Он
занимает стенд целиком, поэтому в общий прогон не входит.

## Что где лежит

| Где | Что |
|---|---|
| `test_*.py` в корне пакета | тесты **устройства**: нужен собранный стенд и живой Ватериус |
| `selftest/` | тесты **самого стенда**: разбор лога и брокер, железо не нужно |
| остальные `*.py` | стенд: роутер, приёмник, брокер, плата, часы, разбор лога, шаблоны Home Assistant (`hatemplates.py`), фасад `Stand` |
| `01_`, `02_`, `03_*.md` | платы стенда: как ввести в строй и чем они болеют |
| `05_air-and-loss.md` | эфир стенда: перекрывающиеся каналы, потерянный сегмент и оборванные тела посылок |
| `04_not-tested.md` | проверки, которые стенду не по силам, и что для них нужно |
| `rescue.py` | вернуть стенд в рабочее состояние после упавшего прогона |
| `ruff.toml` | правила линтера: стенд - такой же код и гниёт так же |

Тесты стенда отделены от тестов устройства не для красоты: первые гоняются в
любой момент и на любой машине, вторым нужен стенд и часы времени.

## Как устроен тест

```python
@pytest.mark.needs(ctype0=LEAKAGE)
def test_E4a_sensor_bounce_gives_one_session(stand, quiet):
    stand.reset_observers()
    stand.dut.wet(channel=0, closed=True)

    session = stand.wait_session(timeout=ALARM_WAIT_S, mode=ALARM_MODE)
    session.assert_alarm(wet0=1)
    ...
```

Вот что делает это возможным.

**Тест объявляет, какие настройки ему нужны, а стенд помнит, какие стоят.**
Требования теста — общие для всех (`Stand.requirements`: сервер и брокер
стенда, часы платы, `BASELINE`) плюс свои из маркера `needs`, именами параметров
прошивки. Стенд держит последнее известное состояние устройства (`state.py`):
посылку, настройки, напечатанные при загрузке, и строки `Saved:` — адресов и
включённости получателей в посылке нет. Перед тестом он сверяет требования с
этим состоянием и настраивает только разницу; всё совпало — лишнего сеанса нет.
Неизвестное состояние читается коротким нажатием. Неизвестным оно становится
после портала, заводского сброса и упавшего теста: там настройки могли
поменяться мимо стенда.

В маркер идут только предусловия. Настройка, которая сама проверяется (дошёл ли
период до attiny, сняла ли смена типа тревогу) или от сеанса которой идёт отсчёт
времени, остаётся в теле теста вызовом `stand.setup()`. Возвращать настройки
в конце теста не нужно: это сделают требования следующего.

**Настройки приезжают в ответе приёмника.** Тело ответа 200 прошивка копирует в
`json_settings`, применяет и тут же отправляет данные повторно. Значит любой
параметр — пороги, вес импульса, период, маска квитанции — ставится из теста без
портала и без брокера. `stand.setup()` дополнительно проверяет, что настройка
действительно применилась: строкой `Apply setting:` в логе и новым значением во
второй посылке.

**Сеанс — один объект.** `wait_session()` сводит лог, посылку и сообщения
брокера. Это важнее, чем кажется: блоки отправки печатаются дважды за сеанс,
а `HTTP: Send OK` одинаков для облака и своего сервера, так что поиск строки по
всему буферу рано или поздно поймает не ту.

**Сеть — контекстные менеджеры.** `stand.net.ap_off()` — сети нет вовсе;
`internet_down()` — сеть есть, трафика нет; `waterius_down()`, `own_server_down()`
и `mqtt_down()` — недоступен ровно один получатель. Последние три не
воспроизвести ничем, кроме правил фильтра, а без них не проверить ни маску
квитанции, ни то, что стенд различает три разные поломки связи.

**Стенд возвращается в исходное состояние после каждого теста.** Две автоматические
фикстуры в `conftest.py`: `clean_net` откатывает правила роутера, `clean_dut` зовёт
`dut.init()` и переводит все четыре линии METF во вход. Именно после, а не до:
упавший тест обязан оставить стенд рабочим.

Иначе оставленная линия живёт до конца прогона. `dut.wet(closed=True)` — это
`pinMode(OUTPUT)` плюс `digitalWrite(LOW)` до отдельной команды, и тест, упавший
между замыканием входа и своим `finally`, дарит следующему вечную тревогу датчика
или лишние импульсы. Начало прогона закрыто отдельно: `Stand.create()` зовёт
`dut.init()` при подъёме сессии.

**Нажатие на кнопку видно глазами.** Пока стенд держит линию кнопки прижатой, на
METF горит зелёный светодиод (`dut.py`, `LED_PRESSED`). Гаснет он только после
того, как линия отпущена, поэтому горящий светодиод при простаивающем стенде
означает ровно одно: прогон убили посреди нажатия и teardown не отработал. Плата
без индикатора прогон не роняет — один раз предупреждает в лог.

## Портал

Отдельный блок тестов (`test_portal.py`, метка `portal`). Стенд удерживает
кнопку, Ватериус поднимает свою точку доступа, и AT-плата - единственный, кто
может в неё зайти, - обходит все адреса портала.

Проверяются три вещи, и каждая ловит свою поломку: страница отдаётся целиком
(образ LittleFS почти полон, и переполнение видно как обрезанный файл, а не как
ошибка сборки); статика совпадает с `ESP8266/data` байт в байт (прошивка и
файловая система шьются разными командами, и залитый по ошибке старый образ
ничем больше не виден); в html не осталось `%PLACEHOLDER%`. Плюс `/api/*` -
разбираемый JSON, и `/api/status/N` без поля `error`, то есть i2c с attiny жив.

Побайтная сверка идёт, только когда версия в устройстве совпадает с версией в
дереве, - иначе тест пропускается с явным текстом. Прошивка и её засады -
[02_nodemcu-at.md](02_nodemcu-at.md).

## Брокер

Брокер поднимается фикстурой в самом процессе pytest (`broker.py`, пакет
`amqtt`) — внешний mosquitto не нужен: его ставят руками, на каждой машине
по-своему, и его отсутствие превращало весь блок MQTT в молчаливый пропуск.
Хранилище выключено: переживёт ли удерживаемое сообщение перезапуск брокера —
вопрос к брокеру, а не к прошивке.

**Топик стенд назначает сам, а не угадывает.** Прочитать его неоткуда: в лог
прошивка топик не печатает (`config.cpp`, print_settings), в посылку он не
попадает. Раньше стенд считал устройство настроенным, если в брокере есть хоть
что-то с нужным началом топика, — и попадался: заводской топик устройства
`waterius/<номер чипа>/` (`config.cpp`, начальные настройки) начинается ровно
так же. Проверка не могла отличить настроенное устройство от заводского и
зеленела всегда, а `G1b` потом падал на пустом корне с деревом
`['waterius/6827706']`. Теперь `Stand.ensure_mqtt` назначает топик один раз за
прогон, а принят он или нет — видно по строке `Saved:`, которую сверяет
`stand.setup()`.

Две вещи, на которых легко получить ложный результат.

**Флаг retain в живой доставке всегда нулевой.** Брокер выставляет его только
тому, кто подписался уже после публикации (MQTT 3.1.1, 3.3.1.3), поэтому
`test_I7` смотрит не на подписчика стенда, а на то, что видит новый —
`MqttWatch.fetch_retained`.

**У amqtt есть дефект, из-за которого стенд менял бы поведение устройства.**
При подключении клиента брокер рассылает ему удерживаемые сообщения по всем
фильтрам, какие зарегистрировал хоть кто-нибудь, а не по его собственным
(`amqtt/broker.py`, цикл `for topic in self._subscriptions` в обработчике
подключения). Ватериус на каждое полученное сообщение публикует пустое с
флагом retain (`ha/subscribe.cpp`, `clear_retained`), то есть из-за подписки
стенда на `#` он вычистил бы retain у собственных показаний и у автодискавери.
`broker.py` накладывает заплату наследником, а `test_broker.py` держит её под
тестом; исправление в апстрим ещё не отправлено.

## Чужие грабли, учтённые здесь

Соседний стенд (репозиторий `metf`, `docs/testspec/hil.md`) проверяет плату METF
тем же способом и уже заплатил за ошибки, которых у нас не было только по
везению. Что из этого стоит в коде:

- **канал роутера проверяется до отправки** (`router.py:set_ap_channel`). Со
  страной `01` прошивка принимает 12-13 молча, кладёт в NVS и при следующем
  старте падает в `abort()` до запуска консолей: команду отдать нечем, чинится
  прошивальщиком. Общее правило - аргумент команды, применяемой после
  перезагрузки, проверяет клиент;
- **перезагрузка доказывается аптаймом** (`router.py:restart`), а не живым
  сокетом: плата уходит молча, и запись в полуоткрытый сокет проходит успешно.
  Сравнение - не с прежним аптаймом, а с тем, каким он стал бы без
  перезагрузки;
- **готовность консоли - по ответу на команду**, а не по принятому соединению:
  порт принимает раньше, чем консоль отвечает;
- **METF опрашивается до схождения** (`stand.py:_wait_metf`), а не один раз: на
  слабой связи плата переподключается сама, и одна осечка роняла весь прогон;
- **занятый порт приёмника переживается и называется** (`receiver.py:_bind`) -
  порт делится с соседними проектами, и `Errno 48` иначе валит прогон до
  первого теста;
- **набор гоняется задом наперёд** (`pytest --reverse`): зависимость по порядку
  в прямом прогоне сидит в зелёном наборе;
- **канал точки стенда закреплён настройкой** (`stand.py:_ensure_ap_channel`), а
  запасной канал тестов смены канала - тоже (`test_wifi.py:other_channel`):
  номер, выбранный формулой, проверяет удачу, а не прошивку;
- **упавший прогон лечится одной командой** (`python3 -m hil.rescue` из
  `Utils/`, `--check` - только доложить);
- **линтер** (`ruff check Utils/hil`).

Долги, записанные как долги:

- каналы для теста смены канала (`test_wifi.py:other_channel`) выбраны
  рассуждением, а не замером: глухой канал на чужом стенде превратит проверку
  прошивки в проверку удачи;
- сроки ожидания выведены из алгоритма прошивки не везде - арифметика написана
  не у каждого числа;
- доля нестабильных прогонов не измеряется, а без неё повторы остаются
  обезболивающим;
- **почему нажатие вплотную к концу сеанса не доходит до устройства** -
  неизвестно. Что оно не доходит, стенд видит делом: без выдержки
  (`stand.py:settle_before_press`) тесты падают с «сеанс не пришёл» при живом
  устройстве, которое за всё окно не печатает ни строки. Но механизм не
  установлен: по схеме Ватериуса-2 цепь BUTTON_STATE идёт на вход ЕСП, через
  диод D5 на WAKE_UP/MISO (PB1 attiny) и на транзисторы питания, а из этого
  задержка не выводится. Пока выдержка - лекарство без диагноза, и число 2,5 с
  взято со слов владельца стенда.

  Воспроизведение, найденное 25 сентября 2026: **первый заказанный кнопкой
  сеанс после теста с датчиком протечки не приходит вовсе** - устройство за
  180 с не печатает ни строки. Четыре прогона из четырёх, где `D3` шёл следом
  за блоком протечки, умерли в подготовке; в обратном порядке, где перед ним
  шли тесты MQTT, тот же `D3` проходит. Выдержка перед нажатием этот случай не
  лечит. В attiny нажатие прерывает сон независимо от тревог
  (`Attiny85/src/main.cpp`, цикл ожидания), а `alarm_hold_min` подавляет только
  тревожные пробуждения, - значит дело не в них, и копать надо дальше.

  Замер 25 сентября 2026, после того как нажатие стало видно в логе: **нажатие
  доходит до платы**. Отказавший случай выглядит так:

  ```
  01:53:52 тревоги прошлого теста: {0: ['alarm_wet']}, снимаем кнопкой
  01:53:54 линия 1 -> 0 на 500 мс: расписка 202     <- это нажатие сработало
  01:54:03 сеанс: mode=3, посылок 1
  01:54:04 выдержка перед нажатием: 1.2 с после сеанса
  01:54:05 линия 1 -> 0 на 500 мс: расписка 202     <- а это нет: 180 с тишины
  ```

  METF приняла нажатие (`202`) и прижала вывод на 500 мс, а устройство не
  проснулось и не напечатало ни строки. Версия «нажатие не доехало до платы»
  отпадает; остаётся вопрос к самому устройству - почему второе нажатие подряд,
  через пару секунд после конца сеанса, им не видится.

## Прошивка METF

Плата стенда — ESP32-C6 SuperMini с прошивкой из `/Users/dontsov/CODE/metf`.

```bash
ls /dev/cu.*      # порт определять каждый раз: C6 виден как usbmodem*
~/.platformio/penv/bin/pio run -d <metf> -e esp32-c6-super-mini -t upload \
  --upload-port /dev/cu.usbmodemXXXX
```

### Что стенд берёт от каждой версии протокола

Версию плата говорит сама: `GET /version`. Разбор ручек — `docs/api.md` в
репозитории METF; стенд опирается на семь рубежей.

| Версия | Что появилось | Кому это нужно у нас |
|---|---|---|
| 5 | `GET /read/stat` со счётчиком вытесненных строк | `logwatch.py`, проверка потерь лога |
| 6 | сервер NTP на плате | блок N, `clock.py` |
| 8 | `/pulse` отвечает распиской `202`, выдержку держит клиент | `metf.py:pulse`, все импульсы и нажатия |
| 9 | `GET`/`POST /wifi` и страница настройки на `/` | досмотр перед прогоном, возврат платы в домашнюю сеть |
| 10 | поле `problem`: причина обрыва словами | текст в логе прогона вместо кода ядра |
| 11 | заголовок `X-Uptime-Ms` в каждом ответе | видно перезагрузку платы: `metf.py:_note_uptime` |
| 12 | `GET /read?ack=` и заголовок `X-Log-Seq` | потерянный ответ не уносит строки лога |

Минимум для прогона — **12**: на меньшей стенд отказывается стартовать
(`metf.py:check`). Прежние рубежи в него входят и отдельно не проверяются. Проверено на плате стенда 24 сентября 2026: протокол 12.

### Сеть платы

**Сетей у платы две, и запомненная сильнее зашитой.** Имя и пароль
компилируются внутрь прошивки из `secrets.ini` (файл не коммитится) флагами
`SSID_NAME`/`SSID_PASS`. С девятого протокола плату можно увести в другую сеть
без пайки — через `POST /wifi action=set` или страницу `/`, — и это она
запоминает во флеше: запомненная сеть перекрывает зашитую и переживает
перезагрузку. Какая сеть сейчас в силе, видно в `GET /wifi` полем `source`:
`build` — из прошивки, `saved` — из памяти.

Прошивка с другими кредами уводит плату в другую сеть и на другой адрес, и
стенд, который ищет её по `host` из `stand.ini`, просто перестаёт получать
ответы — без единой ошибки, по таймауту. Поэтому перед каждой заливкой
сверяйтесь с `secrets.ini`: на плату попадёт то, что лежит в файле, а не то, что
на ней стоит сейчас. Свой адрес плата печатает в USB-консоль (115200) при
старте, там же видно, к какой сети она подключается, её MAC, шлюз и маску.

Вернуть плату к зашитой сети — одна команда, отвечает `202 accepted`, применяет
из главного цикла:

```bash
curl -d action=forget http://<адрес METF>/wifi
curl -s http://<адрес METF>/wifi        # source снова build
```

**Самая дорогая беда: плата на точке стенда.** Прерванный прогон оставил METF
подключённой к `waterius_stand`, она это запомнила, и достать её оттуда удалось
только временным пробросом порта на роутере — управляющий канал стенда оказался
внутри той самой сети, которую тесты гасят. Стенд теперь отказывается
стартовать, если `GET /wifi` называет сеть стенда, и печатает команду возврата.

**Скан забирает радио.** `POST /wifi action=scan` держит плату несколько секунд,
и на это время встаёт всё, что она отвечает, включая NTP. Ничего не отмеряйте
через скан; поле `scanning` в `GET /wifi` показывает, идёт ли он.

Одного SSID мало, если точек с таким именем две: плата ляжет на ту, что
ответила первой, и это может быть другая подсеть. Так и случилось — плата ушла
в сеть, недоступную со стенда, и вернулась только после смены имени сети в
`secrets.ini`. MAC в баннере для того и печатается: по нему адрес закрепляется
на роутере.

### Сервер времени

С протокола 6 плата умеет отдавать NTP на порту 123 — это и есть источник
времени для блока N. Своих часов у неё нет: момент назначает тест, дальше время
идёт от `millis()`. Так проверки синхронизации не зависят ни от интернета, ни от
серверов на машине с прогоном, а тест может назначить узнаваемое время и
подвинуть часы, не дожидаясь суток.

Слушатель сам не поднимается — его включает стенд в начале прогона
(`Stand.ensure_clock`) и переводит на него устройство. Прошивка платы ниже
шестой версии — отказ на старте, а не предупреждение: иначе время тихо
пришло бы из интернета, и прогон зависел бы от него, ничем этого не показав.

Часы платы держатся на `millis()` и пропадают при её перезагрузке, поэтому
перед каждым тестом стенд проверяет `/ntp/stat` и при нужде поднимает их
заново (`Stand.arm_clock`) — один HTTP-запрос, без сеанса устройства.

Проверки самой платы живут в её репозитории: `pytest test/board --metf-host <ip>`.

## Прошивка Ватериуса на стенде

Модель платы определяет окружение: `"model":2` в посылке (или 4 МБ флеша) —
это `waterius_2`, `esp01_1m` — классика на 1 МБ. Залить не то окружение можно
незаметно: собирается и шьётся всё одинаково.

```bash
~/.platformio/penv/bin/pio run -d ESP8266 -e waterius_2               # прошивка
~/.platformio/penv/bin/pio run -d ESP8266 -e waterius_2 -t buildfs    # образ статики
esptool --port <порт> --baud 115200 --connect-attempts 0 write-flash \
  0x0        ESP8266/.pio/build/waterius_2/firmware.bin \
  0x300000   ESP8266/.pio/build/waterius_2/littlefs.bin
```

Оба образа — **одним вызовом** `esptool`: между записями чип остаётся в
загрузчике. Разбив на две команды, вторую придётся ловить заново (`CLAUDE.md`,
«GOTCHA»), а забыв — получить рассогласованную пару, о которой ниже.

**Питание ЕСП даёт attiny, и только на сеанс.** Короткое нажатие — две минуты
(`WAIT_ESP_MSEC`), длинное — десять (`SETUP_TIME_MSEC`). Поэтому `esptool`
запускают с `--connect-attempts 0` и жмут кнопку: он ждёт появления питания сам.
Пока ЕСП сидит в загрузчике, она не говорит attiny «сплю», и окно выбирается
целиком. Запись первых 658 КБ с нуля не трогает ни настройки (они в EEPROM выше
образа), ни файловую систему.

**Прошивка без файловой системы выглядит здоровой.** Устройство отвечает
правильной версией в логе, страницы открываются, а статика на нём — от прошлого
выпуска. Стенд это ловит: `P1` падает на новой странице (`/alarms.html: 404`),
`P3` — на всех файлах сразу («14248 байт против 15250 в образе»).

**Программатор перед прогоном отключайте.** Оставленный на плате USB-TTL держит
ЕСП в загрузчике: `esptool` подключается мгновенно и печатает `Stub flasher is
already running`, а лог пуст — METF не получает ни строки, кнопка ничего не
даёт, и стенд видит мёртвое устройство. Линия сброса до платы при этом не
доходит, так что `esptool ... run` не помогает: выйти из загрузчика можно только
снятием питания.

## Чего не хватает в METF

**Серия импульсов задаётся с компьютера.** На каждый фронт наматывается сетевая
задержка. Тревогам она теперь безразлична - окно объёма нарезано слотами по пять
минут, а квант тишины считается четвертями часа, - но точность прироста показаний
и короткие импульсы электронного входа от неё зависят. `dut.py` уже умеет звать
`/pulse` (выдержка на плате) и откатывается на два запроса, если метода в клиенте
нет; для ритмичных серий нужен `/pulse_train` на самой плате.

**Проверка потерь требует METF 5 и клиента 0.4** (опубликован на PyPI, в
`requirements.txt` затребован). Кольцо лога платы расширено до
64 КБ (511 строк по 128 символов — полный сеанс Ватериуса занимает 193), а
вытесненные строки считаются и отдаются в `GET /read/stat`. `LogWatcher` снимает
счётчик по краям каждого ожидания и валит тест, если за это время кольцо
что-нибудь выбросило: молчаливая потеря делает ложно-зелёным и «сеанс пришёл», и
«сеанса не было». Если плата всё же окажется с прошивкой младше 5 (`/read/stat`
подхватит обработчик `/read`) или клиент - старый, проверка выключается с
предупреждением в лог, а прогон идёт как раньше: обновление платы не должно быть
условием запуска.

### Известные дефекты под xfail

Тест описывает правильное поведение и падает на нынешней прошивке. Метка
`xfail(strict=True)`: исправят - тест станет `XPASS`, прогон покраснеет, и
метку снимут осознанно.

| Тест | Что не так | Где |
|---|---|---|
| `test_S4_invalid_value_is_rejected[ctype_unknown]` | тип входа с сервера и из HA уходит в attiny без проверки | `active_point_api.cpp`, applyInputParameter |
| `test_S4b_rejected_period_keeps_tuning` | отвергнутый `period_min` всё равно сбрасывает подстройку | `active_point_api.cpp`, applyNonCheckBoxParameter |
| `test_W3_unusual_network_names[ssid_32]` | имя сети в 32 байта не сохраняется | `core/types.h`, WIFI_SSID_LEN |
