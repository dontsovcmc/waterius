# WT32-ETH01: точка доступа стенда

Стенду нужна не «какая-нибудь» точка доступа, а такая, которую можно погасить,
переименовать, переставить на другой канал и заставить резать трафик выборочно —
из кода, без рук. Домашний роутер этого не даёт, телефон тем более. Даёт плата
WT32-ETH01 с прошивкой [esp32_nat_router](https://github.com/martin-ger/esp32_nat_router):
аплинк у неё по витой паре, поэтому радио свободно и канал наш.

Отсюда же главное правило всей настройки: **управление идёт по проводу**. Стенд
командой `ap disable` гасит Wi-Fi — если бы канал управления шёл по тому же
радио, команда отрубила бы саму себя.

В конце этой инструкции `python router.py --host <ip> show config` отвечает, а
`pytest Utils/hil --stand` доходит до проверок прошивки.

## Что понадобится

| Что | Зачем |
|---|---|
| WT32-ETH01 | сама плата |
| Переходник USB-TTL 3,3 В | **только для первой прошивки** и для восстановления |
| Источник питания 5 В или 3,3 В | питать плату отдельно от переходника |
| Патч-корд | аплинк в домашний роутер |
| `esptool` | `pip install esptool`; проверено на 5.2.0 |
| Каталог `firmware_wt32_eth01` | четыре образа прошивки, см. «Что скачать заранее» |

Питание подаётся **либо** на вывод `5V`, **либо** на `3V3` — не на оба сразу.
Средний ток по документации платы около 80 мА, но пики при поднятом Ethernet-PHY
и радио заметно выше, поэтому берите источник с запасом. Типичная неудача при
прошивке — питание от самого переходника: его не хватает, и плата сбрасывается
посреди записи.

## 1. Прошивка — единственный шаг через USB

У платы нет своего USB, а на чистом ESP32 нет ни сети, ни загрузчика по воздуху:
первый образ заливается только по UART. Дальше переходник не нужен — обновления
идут по сети через страницу `/config`, настройки при этом сохраняются.

**Схема.** RX и TX перекрещиваются:

| USB-TTL | WT32-ETH01 |
|---|---|
| `GND` | `GND` |
| `TX` | `RX0` |
| `RX` | `TX0` |
| — | питание на `5V` **или** `3V3` от отдельного источника |

**Режим загрузки.** Замкнуть `IO0` на `GND` (они соседние, рядом с `RX0`) и
только после этого подать питание.

Нужна сборка с проводным аплинком — каталог `firmware_wt32_eth01`; в обычной
сборке нет даже команды смены канала.

**Найти порт.** Имя меняется от переходника к переходнику и от сеанса к сеансу —
ищите его, не подставляйте из примера:

```bash
ls /dev/cu.usbserial-*
```

**Убедиться, что чип отвечает.** Команда ничего не пишет, только читает:

```bash
esptool --chip esp32 -p /dev/cu.usbserial-XXXX --before default_reset --after no-reset flash_id
```

Ответ должен содержать `Detected flash size:` и `Flash voltage set by a strapping
pin: 3.3V`. Если вместо этого таймаут — плата не в загрузчике: см. «Если не
получается».

**Стереть и записать.** Обе команды выполняются из каталога со сборкой:

```bash
cd ~/CODE/esp32_nat_router

esptool --chip esp32 -p /dev/cu.usbserial-XXXX erase_flash

esptool --chip esp32 -p /dev/cu.usbserial-XXXX \
  --before default_reset --after hard-reset \
  write_flash -z --flash_mode dio --flash_freq 40m --flash_size detect \
  0x1000  firmware_wt32_eth01/bootloader.bin \
  0x8000  firmware_wt32_eth01/partition-table.bin \
  0xf000  firmware_wt32_eth01/ota_data_initial.bin \
  0x20000 firmware_wt32_eth01/esp32_nat_router.bin
```

Если плата уже осталась в загрузчике после предыдущей команды (`Staying in
bootloader`), в обеих командах вместо `--before default_reset` берите
`--before no-reset` — именно так эта плата и прошивалась.

Запись большого образа идёт около полутора минут на 115200.

> **Адрес приложения — `0x20000`.** Страница вики проекта «WT32-ETH01» называет
> `0x10000`. Это неверно для сборки с OTA-разметкой: в ней четыре части, и
> `ota_data_initial.bin` занимает `0xf000`. Прошитая по `0x10000` плата не
> загрузится. Истина — в `manifest_wt32_eth01.json`.

**Признак успеха:** `Hash of data verified.` для всех четырёх файлов.

**Снять перемычку и передёрнуть питание — обязательно.** Пока `IO0` притянут к земле, чип
после каждого сброса уходит в загрузчик и приложение не стартует: esptool с платой
разговаривает прекрасно, а консоль молчит и точка доступа не появляется. На этой плате у
перемычки есть и второй эффект — `GPIO0` занят тактированием Ethernet, так что с ней сеть не
поднимется в любом случае.

Проверка, что приложение пошло:

```bash
python3 -m serial.tools.miniterm /dev/cu.usbserial-XXXX 115200
```

Нажать Enter — прошивка отвечает приглашением `esp32>`, команда `version` печатает версию
IDF и параметры чипа. Загрузочный баннер к этому моменту уже проехал, ловить его не нужно.
Выход из терминала — `Ctrl+]`. Переходник после этого можно отложить.

То же самое инструментом стенда, без терминала:

```bash
python3 Utils/hil/router.py --port /dev/cu.usbserial-XXXX show status
```

**На переходнике от ESP-01 перемычка может не понадобиться.** Такие переходники заводят
сброс на управляющую линию, и `esptool` вводит плату в загрузчик сам. Проверено: прошивка
прошла без ручного замыкания `IO0`. Начните без перемычки; ставьте её, только если `esptool`
не может синхронизироваться.

## 2. Провод и адрес

Воткнуть патч-корд в домашний роутер, подать питание. Плата получает адрес по
DHCP. Найти его можно двумя способами.

По списку клиентов домашнего роутера — по MAC платы. Или, если списка нет под
рукой, обойти свою подсеть и спросить у каждого адреса, не плата ли это
(подставьте свою подсеть вместо `192.168.50`):

```bash
for i in $(seq 1 254); do ip=192.168.50.$i; \
  (curl -s -m 1 "http://$ip/" | grep -q 'ESP32 NAT Router' && echo "плата: $ip") & \
done; wait
```

Способ надёжнее пинга: он опознаёт плату по её же странице, а не по факту
отклика. Питания от USB-порта домашнего роутера на аплинк хватает — проверено.

**Закрепите этот адрес за MAC** (DHCP reservation на домашнем роутере): он
попадёт в `stand.ini`, и плавающий адрес каждый раз ломал бы стенд.

Статический адрес на самой плате не советую: при переезде стенда в другую сеть
плата станет немой, и достучаться до неё можно будет только по USB.

## 3. Веб-интерфейс — сразу и по проводу

Откройте `http://<ip>` в браузере. Настраивать для этого ничего не нужно:
веб-сервер включён по умолчанию, а список разрешённых интерфейсов по умолчанию —
все (`s_web_bind = RC_BIND_AP | RC_BIND_STA | RC_BIND_VPN` в
`components/http_server/http_server.c`). В сборке с проводным аплинком `STA` —
это и есть Ethernet.

На странице состояния должен быть виден аплинк с тем же адресом.

## 4. Удалённая консоль

Стенд ходит на плату не через браузер, а по TCP-консоли — её и включаем. Всё
делается командами: браузер нужен только если хочется посмотреть глазами.

> **Пароль стенда — `12345678`.** Это лабораторный стенд в своей сети: пароль
> общий, известный и записан здесь намеренно, чтобы настройку можно было
> повторить без переписки. Никуда, кроме стенда, его не переносите.

**Порядок важен: сначала консоль, потом пароль.** Пока пароля нет, веб-интерфейс
пускает без авторизации, и настройка делается одной командой. После установки
пароля пришлось бы возиться с сессией и cookie.

**Включить консоль.** Параметры идут в строке запроса: `/config` отвечает только
на GET, POST на него даёт `405`.

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  "http://192.168.50.236/config?rc_save=1&rc_enabled=1&rc_port=2323&rc_bind_ap=1&rc_bind_sta=1&rc_timeout=0"
```

Ответ `303` — принято. Проверить, что применилось:

```bash
curl -s "http://192.168.50.236/config" | tr '<' '\n' | grep -E "rc_enabled|rc_port|rc_bind"
```

В строках `rc_enabled value='1'`, `rc_bind_ap` и `rc_bind_sta` должно стоять
`checked`.

> **`sta` — это Ethernet.** В блоке консоли интерфейс подписан `STA`, а в блоке
> веб-интерфейса тот же самый — `ETH`; команда `remote_console bind` слово `eth`
> не принимает вовсе. Проверка входящего соединения сравнивает адрес с адресом
> аплинка, а он в этой сборке приходит по событию `IP_EVENT_ETH_GOT_IP`. Значит
> `ap,sta` и означает «слушать на витой паре». `ap` в списке — запасной вход с
> самой точки доступа, если провод выдернут.

**Поставить пароль.** Здесь, наоборот, форма ждёт POST на корень:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST "http://192.168.50.236/" \
  --data "new_password=12345678&confirm_password=12345678"
```

Ответ `303`. После этого главная страница отдаёт форму входа вместо настроек —
это и есть признак, что защита включилась.

**Проверить консоль.** Перезагрузка не нужна, настройки применяются сразу:

```bash
python3 Utils/hil/router.py --host 192.168.50.236 --password 12345678 show status
```

Должно напечатать `Uplink ETH: connected`, адрес платы и `AP interface: enabled`.

**И сразу главная проверка смысла всей затеи** — гасим Wi-Fi по проводу:

```bash
python3 Utils/hil/router.py --host 192.168.50.236 --password 12345678 ap off
python3 Utils/hil/router.py --host 192.168.50.236 --password 12345678 show status   # AP interface: disabled
python3 Utils/hil/router.py --host 192.168.50.236 --password 12345678 ap on
python3 Utils/hil/router.py --host 192.168.50.236 --password 12345678 show status   # AP interface: enabled
```

Точка пропала и вернулась, а управление не прервалось ни на секунду. Ради этого
и брали плату с проводным аплинком.

## 5. Настройка точки доступа

Теми же командами, которыми потом ходит `router.py`. Имя и пароль точки —
рабочие для стенда; Ватериус настраивается на них же.

```bash
R="python3 Utils/hil/router.py --host 192.168.50.236 --password 12345678"

$R raw "set_ap waterius_stand 12345678"
$R raw "set_ap_channel 6"          # печатает: Restart the device for changes to take effect
$R raw "client_stats enable"       # печатает: Per-client stats enabled
$R raw "restart"
```

`set_ap_channel` существует только в сборке с проводным аплинком — при аплинке
по Wi-Fi радио одно, и точка обязана жить на канале роутера. Канал 6 выбран
произвольно; берите тот, что свободнее у вас.

Плата поднимается секунд за десять. Дождаться и проверить, что всё село в NVS
(отдельной команды сохранения нет):

```bash
until $R raw "version" >/dev/null 2>&1; do sleep 3; done
$R show config
```

Ожидается:

```
AP Settings:
  SSID: waterius_stand
  Channel: 6
Web Interface: enabled (port 80, bind: AP ETH VPN )
```

**Закрепить адрес за Ватериусом** — чтобы правила фильтра не переписывать после
каждой выдачи адреса. MAC берётся из списка клиентов, когда устройство впервые
подключится к точке (`$R show clients`), либо из его собственного лога — прошивка
печатает `IP: MAC Address:` в каждом сеансе.

```bash
$R raw "dhcp_reserve add <mac_ватериуса> 192.168.4.100"
$R show mappings          # запись должна появиться: <mac> -> 192.168.4.100
```

> **Имя устройства не указывать.** Вики проекта документирует форму
> `dhcp_reserve add <mac> <ip> -- <имя>`, но эта сборка её отвергает:
> `dhcp_reserve: excess option`. Резервирование при этом не создаётся.

## 6. Приёмка стендом

В `stand.ini`:

```ini
[router]
port =                      ; оставить пустым!
host = <ip платы>
password = <пароль роутера>

[dut]
mac = <MAC Ватериуса>
ip  = <адрес из dhcp_reserve>
```

> **`port` не заполнять.** `router.py::connect` предпочитает `port` над `host` и
> молча уведёт управление обратно на USB — а там оно ничем не лучше Wi-Fi:
> провод придётся тянуть к плате постоянно. `port` нужен только для
> восстановления.

```bash
python Utils/hil/router.py --host <ip> show config
python Utils/hil/router.py --host <ip> ap off && python Utils/hil/router.py --host <ip> ap on
python Utils/hil/router.py --host <ip> raw "acl to_ap TCP <dut_ip> * any 80 deny"
python Utils/hil/router.py --host <ip> raw "show acl"
python Utils/hil/router.py --host <ip> unblock

cd ../..
python3 -m pytest Utils/hil --stand -k "G3 or G4 or G5" -v
python3 -m pytest Utils/hil --stand -m "not slow" -v
```

## Если не получается

| Симптом | Причина |
|---|---|
| `esptool` не видит плату | не замкнут `IO0` на `GND`, либо замкнули после подачи питания |
| Прошивка срывается на середине | питание от переходника — нужен отдельный источник |
| Плата отвечает, но пишет мусор | перепутаны `RX0`/`TX0` — они перекрещиваются |
| Прошилась, но не загружается | приложение записано по `0x10000` вместо `0x20000` |
| `esptool` работает, а консоль молчит и точки доступа нет | не снята перемычка `IO0`–`GND`: плата каждый раз уходит в загрузчик |
| `Uplink ETH: not connected` при воткнутом проводе | не хватает питания на Ethernet-PHY — питать плату отдельно, не от переходника |
| Веб-интерфейс не открывается по проводу | нет линка или адрес взят не тот; проверьте список клиентов домашнего роутера |
| `nc <ip> 2323` молчит | консоль не включена, либо в bind нет `sta`, либо не было перезагрузки |
| Тесты не видят роутера | в `stand.ini` заполнен `port` — управление ушло на USB |
| `405` на настройку через `curl` | `/config` отвечает только на GET: параметры идут в строке запроса, а не телом |
| Веб-интерфейс требует вход, а настроить надо | пароль уже стоит; настраивайте до установки пароля либо снимите его: `factory_reset` |
| `dhcp_reserve` не создаётся | указано имя через `--`: прошивка отвечает `excess option`, форма из вики не работает |
| Правило фильтра не появляется | лишнее слово `add`: синтаксис `acl <список> <proto> <src> [<порт>] <dst> [<порт>] <действие>` |
| Правило есть, а трафик идёт | взят не тот список: исходящий трафик клиента режет `to_ap`, см. ниже |
| Клиент точки получил адрес, но наружу не ходит | не работает NAT — см. ниже |

### Списки фильтра названы от лица интерфейса, а не клиента

Чтобы зарезать то, что **клиент точки отправляет наружу**, правило заводится в
списке **`to_ap`**, а не в `from_ap`, как подсказывает имя. Причина в том, где
стоят обработчики: пакет клиента приходит на интерфейс точки, то есть попадает
в обработчик входа, а тот сверяется с `ACL_TO_AP` (`netif_hooks.c`:
`ap_netif_input_hook` -> `ACL_TO_AP`, `ap_netif_linkoutput_hook` ->
`ACL_FROM_AP`). Автор применил к интерфейсу точки то же правило «вход - это
`to_`», что и к аплинку.

Правило в `from_ap` с адресом устройства в источнике не совпадёт никогда: там
проверяются пакеты, идущие **к** клиенту, и источником в них стоит удалённый
узел. Фильтр при этом молча ничего не режет — ни ошибки, ни попаданий:

```shell
# так - не работает, хотя правило заводится и видно в show acl
acl from_ap IP 192.168.4.101 any deny
# так - работает: denied растёт, клиент наружу не ходит
acl to_ap   IP 192.168.4.101 any deny
```

Проверено на живой паре: с правилом в `to_ap` пинг с клиента даёт ERROR и
счётчик `denied` растёт, без правила — проходит. То же с портом:
`acl to_ap TCP <ip> * any 80 deny` рубит только TCP на 80-й, ICMP продолжает
ходить.

### Клиенты точки видят только саму точку

Самая дорогая по времени поломка: снаружи всё выглядит исправным. Клиент
получает адрес по DHCP, пингует `192.168.4.1`, открывает веб-интерфейс платы —
и не достаёт больше ничего: ни машину в проводной сети, ни `8.8.8.8`, ни DNS.
Ватериус в такой сети пишет в лог `HTTP: Response code: -1` на каждую попытку.

Обманчивы обе привычные проверки. `ping` **с самой платы** проходит: она ходит
своим стеком через Ethernet, и трансляции ему не нужно. `show config` про NAT
не пишет вовсе, а `show acl` показывает нули в счётчиках — но счётчики растут
только при заведённых правилах (`netif_hooks.c`: проверка начинается с
`if (!acl_is_empty(...))`), так что нули не означают, что пакетов не было.

Состояние печатает только `set_ap_nat` без аргументов, а чинится перезапуском:

```shell
python3 Utils/hil/router.py --host <ip> --password <пароль> nat        # состояние
python3 Utils/hil/router.py --host <ip> --password <пароль> nat on     # и перезагрузка
```

Проверять — с клиента, а не с платы: `AT+PING="8.8.8.8"` с AT-платы,
подключённой к точке стенда, либо просто прогон стенда — `Stand.ensure_network`
требует, чтобы посылка дошла до приёмника, и в тексте ошибки печатает состояние
NAT.

Причина — ошибка в самой прошивке роутера: в сборке с проводным аплинком NAT не
включается заново после `ap enable`, потому что обработчик старта точки в этой
ветке его не трогает, в отличие от ветки с Wi-Fi-аплинком. Разбор, патч и
измерения — [router-nat-bug.md](router-nat-bug.md). Стенд обходит это
перезагрузкой платы после каждого `ap_off()`.

Вторая, отдельная ловушка: форма настроек веб-интерфейса пишет `ap_nat=0`, если
в запросе нет галочки — обработчик берёт значение как «есть параметр или нет», а
не как «что в нём написано». То есть настройка платы через `curl` со строкой
запроса — а именно так удобнее всего задавать SSID и пароль — молча выключает
NAT, если не перечислить заодно все галочки. Поэтому после любой настройки через
веб-интерфейс делайте `restart` и проверяйте связь с клиента.

## Сброс и восстановление

**Кнопкой BOOT сбросить нельзя**: на этой плате `IO0` занят тактированием
Ethernet, и заводского сброса по кнопке нет. Остаётся два пути:

- `factory_reset` в консоли — стирает настройки (пространство NVS `esp32_nat`);
- `esptool --chip esp32 -p <порт> erase_flash` и прошивка заново — если пароль
  забыт и в консоль не попасть.

Второй путь требует переходника. Это единственная причина держать его под рукой
после первой прошивки.
