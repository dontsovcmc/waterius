# NAT точки доступа стенда пропадает после `ap disable` / `ap enable`

Ошибка в прошивке роутера стенда — [martin-ger/esp32_nat_router](https://github.com/martin-ger/esp32_nat_router),
в сборке с проводным аплинком (`CONFIG_ETH_UPLINK`), то есть ровно в той, что
стоит на WT32-ETH01. Найдена 07.09.2026 при первом же прогоне сетевых тестов.
Здесь всё, что выяснено, — чтобы вернуться и оформить исправление в апстрим.

**Состояние:** исправление не отправлено. В стенде живёт обход (см. ниже).

## Как выглядит

Клиент точки доступа получает адрес по DHCP, пингует саму точку (`192.168.4.1`),
открывает её веб-интерфейс — и не достаёт больше ничего: ни машину в проводной
сети, ни `8.8.8.8`, ни DNS.

Ватериус в такой сети пишет в лог на каждую попытку:

```
HTTP: URL:http://192.168.50.252:8000/data
HTTP: Post request
HTTP: Response code: -1
```

и так три раза по 12 секунд, после чего `HTTP: Failed send data`. То же самое с
`https://cloud.waterius.ru`. Со стороны это неотличимо от «приёмник не работает»
или «прошивка Ватериуса не умеет отправлять».

## Почему это тяжело поймать

Все привычные проверки говорят, что всё в порядке.

| Проверка | Что показывает | Почему обманывает |
|---|---|---|
| `ping` с самой платы (`ping 8.8.8.8` в консоли роутера) | проходит, 20 мс | плата ходит своим стеком через Ethernet, трансляция ей не нужна |
| `set_ap_nat` без аргументов | `NAT: enabled` | печатает переменную в памяти, а не то, включён ли NAPT на интерфейсе |
| `show config` | про NAT молчит вовсе | — |
| `show acl` | счётчики по нулям | счётчики растут только при заведённых правилах: проверка в `netif_hooks.c` начинается с `if (!acl_is_empty(...))`, так что нули не означают, что пакетов не было |
| `show status` | `Uplink ETH: connected`, адрес есть | аплинк действительно исправен |

Единственная честная проверка — **с клиента точки**: `AT+PING="8.8.8.8"` с
AT-платы, подключённой к точке стенда (см. [02_nodemcu-at.md](02_nodemcu-at.md)), либо
`AT+CIPSTART` на любой адрес за пределами `192.168.4.0/24`.

## Причина

Прошивка включает NAPT в нескольких местах, и эти места **асимметричны** между
сборкой с Wi-Fi-аплинком и сборкой с Ethernet-аплинком.

| Момент | Wi-Fi-аплинк (`#else`) | Ethernet-аплинк (`#if CONFIG_ETH_UPLINK`) |
|---|---|---|
| `WIFI_EVENT_AP_START` | `ip_napt_enable(my_ap_ip, 1)`, строки 736–740 | только `init_ap_netif_hooks()`, строки 469–471 — **NAPT не включается** |
| Аплинк получил адрес | есть, строки 725–728, с комментарием «Re-enable NAPT here in case the AP cycled» | в `IP_EVENT_ETH_GOT_IP` (строки 428–463) делается всё — portmap, DNS, маршрут VPN, счётчики, SNTP, syslog — **кроме NAPT** |

Строки — по `main/esp32_nat_router.c` в master на 07.09.2026 (проверено: файл,
выкачанный с GitHub, побайтно совпадает с локальной копией `1157ae2`).

Значит, в ETH-сборке трансляция включается ровно дважды:

1. в `app_main` при старте (строки 1509–1511);
2. в `ap_set_enabled(true)` (строки 800–818) — сразу после `esp_wifi_start()`.

Второй вызов идёт **синхронно за асинхронным стартом**: `esp_wifi_start()`
возвращает управление раньше, чем поднимется интерфейс точки и придёт событие
`WIFI_EVENT_AP_START`. В Wi-Fi-сборке это неважно — там обработчик `AP_START`
включает NAPT ещё раз, и автор прямо пишет об этом в комментарии («Re-enable
NAPT on every AP start»). В ETH-сборке такого обработчика нет, и чинить некому.

Отсюда наблюдаемое: после `ap disable` → `ap enable` NAT не возвращается до
перезагрузки платы.

Тот же провал должен случаться при переполучении адреса на Ethernet — обрыв
линка, продление аренды DHCP, — потому что `IP_EVENT_ETH_GOT_IP` тоже не
включает NAPT, тогда как парный ему `IP_EVENT_STA_GOT_IP` включает.

## Исправление

Две строки, зеркально Wi-Fi-ветке.

В `wifi_ap_event_handler` ETH-сборки:

```c
    if (event_id == WIFI_EVENT_AP_START) {
        ESP_LOGI(TAG, "AP started");
        init_ap_netif_hooks();
        /* Re-enable NAPT on every AP start: esp_wifi_start() returns before
           the AP netif is up, so the enable in ap_set_enabled() can be lost. */
        if (ap_nat_enabled && my_ap_ip != 0)
            ip_napt_enable(my_ap_ip, 1);
    } else if (...)
```

И в `eth_event_handler`, в ветке `IP_EVENT_ETH_GOT_IP`, перед
`xEventGroupSetBits(...)`:

```c
        /* Same as the STA uplink path: the AP may have cycled since the
           initial ip_napt_enable in app_main. */
        if (ap_nat_enabled)
            ip_napt_enable(my_ap_ip, 1);
```

## Обход в стенде

`NatRouter.ap_off()` после `ap enable` перезагружает плату. Стоимость замерена
на живом стенде дважды подряд, отсчёт от момента отправки `restart`:

| Что | Прогон 1 | Прогон 2 |
|---|---|---|
| Консоль 2323 отвечает на команду | 5,8 с | 5,3 с |
| Клиент точки ходит наружу через NAT | 7,1 с | 8,9 с |

То есть 7–9 секунд; `RESTART_WAIT` в `router.py` — 12 секунд, с запасом. Тестов,
гасящих точку, немного, так что на полном прогоне это меньше минуты.

Мерить готовность консоли по установке TCP-соединения нельзя: порт 2323
принимает подключение раньше, чем консоль готова отвечать, и первая попытка дала
ложные «0,0 секунды».

Вторая страховка — в `Stand.ensure_network()`: после перевода Ватериуса в сеть
стенда тест требует, чтобы посылка дошла до приёмника, и в тексте ошибки
печатает состояние NAT. Так поломка называет себя сама, а не выглядит как
неисправная прошивка счётчика.

## Как воспроизвести

```bash
# точка доступа стенда исправна, клиент (AT-плата) в её сети
python3 Utils/hil/router.py --host <ip> --password <пароль> ap off
python3 Utils/hil/router.py --host <ip> --password <пароль> ap on
# с клиента: AT+PING="8.8.8.8"  ->  ERROR
python3 Utils/hil/router.py --host <ip> --password <пароль> restart
# с клиента через ~8 секунд: AT+PING="8.8.8.8"  ->  OK
```
