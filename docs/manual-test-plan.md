# Ручной прогон перед релизом

Что проверить руками на живом устройстве, в каком порядке и что считать
правильным поведением.

Автотесты закрывают чистую логику плотно: googletest на обе модели, тесты
attiny, тесты строк портала, проверки симулятора — всё это гоняет CI, и
дублировать их руками незачем. Этот план целится туда, куда они не достают:
**железо (i2c, EEPROM, deep sleep, кнопка), настоящий браузер на телефоне, эфир
(Wi-Fi, HTTP, MQTT), Home Assistant и обновление по воздуху.**

Стенд — Ватериус 2. Классика и attiny старее 41 в план не входят: их состояния
перебираются в симуляторе и автотестами, отмечено в тексте.

## Приоритеты

- **P0** — без этого не релизим.
- **P1** — прогнать, если есть день.
- **P2** — глубокая проверка, редкие ветки.

Минимальный прогон = все P0: A1–A9, B1, B3, D1, D2, E1–E6, F1, F2, G1–G4, J5,
X1–X4.

По каждому тесту отмечайте `ID — ok / fail`, при fail — строку лога и что было
на экране.

## Стенд

| Что | Зачем |
|---|---|
| Ватериус 2 с батарейками, attiny 41 | основной объект |
| USB-TTL 3,3 В на TX ЕСП, терминал 115200 8N1 | единственный источник правды по сеансу (`ESP8266/src/setup.h:LOG_BAUD`) |
| Два провода с кнопкой на входы 0 и 1 (замыкание на землю) | импульсы и датчик протечки |
| Телефон и ноутбук | портал проверяется и в окне captive portal, и в обычном браузере |
| Роутер, который можно выключить | сценарии без сети и бюджет внеплановых сеансов |
| Ноутбук в той же сети: приёмник HTTP и mosquitto | свой сервер и брокер |
| Аккаунт на waterius.ru | облачный получатель |

### Прошивка стенда

```bash
~/.platformio/penv/bin/pio run -d ESP8266 -e waterius_2
~/.platformio/penv/bin/pio run -d ESP8266 -e waterius_2 -t buildfs
ls /dev/cu.usbserial-*      # порт определять каждый раз, не хардкодить
~/.platformio/penv/bin/python -m esptool --port <PORT> --baud 460800 write_flash \
  --flash_freq 40m --flash_size 4MB --flash_mode qio \
  0x0 ESP8266/.pio/build/waterius_2/firmware.bin \
  0x300000 ESP8266/.pio/build/waterius_2/littlefs.bin
```

Прошивка и файловая система пишутся **одной командой**. Двумя отдельными второй
заход падает с `Timed out waiting for packet header`: после первой записи ЕСП
уходит в свой цикл и в загрузчик больше не возвращается.

### Приёмник HTTP

Успехом считается только код 200, поэтому приёмник обязан его возвращать
(`ESP8266/src/https_helpers.cpp:post_data`):

```python
# recv.py — python3 recv.py, слушает 0.0.0.0:8000
import http.server, json
class H(http.server.BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers['Content-Length']))
        print(json.dumps(json.loads(body), ensure_ascii=False, indent=1), flush=True)
        self.send_response(200); self.end_headers()
http.server.HTTPServer(('', 8000), H).serve_forever()
```

### MQTT

```bash
mosquitto_sub -h <broker> -t 'waterius/#' -v          # данные
mosquitto_sub -h <broker> -t 'homeassistant/#' -v     # автодискавери
```

### Чем ускорить прогон

Почти всё упирается в период пробуждения. На время тестов поставьте **период 5
минут** на странице «Отправка показаний»: сутки по умолчанию растягивают план на
неделю. Перед финальным прогоном верните 1440 и проверьте расписание (H2).

Импульс на механическом входе: замкнуть **не меньше 300 мс** (опрос 250 мс плюс
подтверждение 50 мс), разомкнуть **не меньше 750 мс** — три пустых опроса подряд
(`Attiny85/src/counter.h:discrete`). Короче — импульс не засчитается, и это не
дефект.

Предусловие: заводской сброс или свежая прошивка.

## C. Проверка ввода

Быстрее всего гоняется в симуляторе — коды ошибок там те же. На железе
достаточно C1 и C5.

| ID | P | Что ввести | Ожидаемо |
|---|---|---|---|
| C1 | P1 | Показания воды `123456` | «Показания воды вводятся с литрами» |
| C2 | P1 | Адрес брокера `mqtts://broker` | «Шифрованное подключение к MQTT не поддерживается» |
| C3 | P1 | Адрес брокера `broker:1883` | «Порт указывайте в отдельном поле» |
| C4 | P1 | Остановка расхода `1093` | «Неверное значение». Потолок 1092 часа, `ESP8266/src/core/idle.h:ALARM_STOP_MAX_HOURS`. Через интерфейс ловится только так: четыре цифры проходят проверку разметки, отвергает прошивка |
| C5 | P1 | Имя сети из двадцати кириллических букв | «Превышена длина поля»: длина считается в байтах, кириллица занимает два |
| C6 | P2 | Открыть настройки Wi-Fi, не трогая пароль, сохранить | Пароль не затирается: поле из одних звёздочек означает «не редактировали» |
| C7 | P2 | Выключить MQTT, вписать заведомо битый адрес брокера, сохранить | Сохранилось без ошибки, значение не изменилось. Так и задумано: поля выключенного транспорта не разбираются (`ESP8266/src/portal/active_point_api.cpp:applySettings`) |

## E. Тревоги

Предусловия для всей группы: attiny 41 (в логе `attiny firmware ver: 41`), вход
считает импульсы, вес задан числом, пороги сохранены **и прошёл хотя бы один
сеанс** — пороги живут в ОЗУ attiny и уезжают туда в каждом сеансе
(`ESP8266/src/main.cpp:send_alarm_config`). Контроль в логе:

```
INFO : Alarm config: interval0=... leak0=... interval1=... leak1=... vacation=0
```

Строки нет или интервалы нулевые — дальше идти бессмысленно.

Что означает каждый режим — [alarms.md](alarms.md).

| ID | P | Настройка | Что подать | Ожидаемо |
|---|---|---|---|---|
| E1 | P0 | вес 10 л/имп, порог расхода 3600 л/ч — это 40 тиков, 10 секунд | два импульса с интервалом меньше 10 секунд | Внеплановый сеанс: `mode: 4`, в посылке `alarm` и `alarm_flow1` равны единице |
| E2 | P0 | то же | пауза дольше 20 секунд | Второй сеанс, `alarm_flow1` ноль. Снятие — такая же новость, как появление. Гистерезис вдвое |
| E3 | P0 | непрерывный расход 2 минуты | импульс раз в 25 секунд ровно, три минуты подряд | Через две минуты ровного ритма `alarm_leak1` равен единице. Пауза дольше двойного интервала снимает тревогу |
| E4 | P0 | вход 0 — «Датчик протечки (замыкание)» | замкнуть вход | Сеанс в течение секунды, `alarm_wet0` равен единице. Разомкнуть — в пределах пяти минут сеанс со снятием |
| E5 | P0 | вход 0 — «Датчик протечки (размыкание)» | выдернуть провод | Тоже тревога: в этом весь смысл нормально-замкнутого датчика |
| E6 | P0 | включён режим «Я уехал» | любые два импульса | Тревога срабатывает и **сама не снимается** — так задумано. Выключение режима возвращает обычные пороги |
| E7 | P1 | период 5 минут, остановка расхода 1 час | ничего не подавать двенадцать пробуждений | `Idle min: 60/...`, в посылке `alarm_stop1` равен единице. Импульс снимает тревогу в том же сеансе |
| E8 | P1 | вес импульса «Авто» | открыть страницу тревог | Пороги видны, но неактивны и серые, под заголовком «Счётчик не настроен» со ссылкой. Остановка расхода при этом активна: её считает ЕСП |
| E9 | P1 | тип входа «Выключен» или датчик протечки | открыть страницу тревог | Блок канала не исчезает: заголовок на месте, вместо полей примечание «Вход не считает импульсы» |
| E10 | P1 | режим «Я уехал» при весе «Авто» | два импульса | Тревога всё равно работает: отпуску известный вес не нужен (`ESP8266/src/core/alarm.cpp:alarm_interval_ticks`) |
| E11 | P2 | вынуть батарейки на минуту и вставить | импульсы до первого сеанса | Тревог нет: пороги в ОЗУ attiny стёрлись. После первого сеанса всё работает. Документированное поведение |

| ID | P | Что делать | Ожидаемо |
|---|---|---|---|
| F1 | P0 | Никого не отмечать в «Кто получает оповещение», вызвать тревогу | В логе `Alarm confirm: mask=0 ... any=1 -> 1`, повторных сеансов нет |

## G. Отправка и светодиод

| ID | P | Что делать | Ожидаемо |
|---|---|---|---|

| G3 | P0 | Испортить пароль Wi-Fi, нажать кнопку | Две вспышки |

| G5 | P1 | Несуществующий брокер, остальное рабочее | Четыре вспышки |
| G6 | P1 | Сбить связь с attiny | Пять вспышек |
| G7 | P2 | Сервер, отвечающий 500 | Шесть вспышек: успехом считается только 200 |

брокер. Одна вспышка про просевшее питание моргает только тогда, когда показания
всё же ушли. Подробности — [sending.md](sending.md).

## I. Home Assistant и управление извне

| ID | P | Что делать | Ожидаемо |
|---|---|---|---|
| I1 | P1 | Включить автодискавери и нажать кнопку | Автодискавери публикуется только в режиме настройки и по кнопке. В HA появляется устройство: показания, вес, серийный номер, тип входа, пороги числами, состояния как `binary_sensor`, режимы как переключатели |

|---|---|---|---|
| J1 | P1 | Собрать образы `ESP8266/scripts/build_and_deploy.sh`, отдать команду обновления через MQTT | В логе `OTA: start`, замер напряжения по трём отсчётам, сначала файловая система, потом прошивка, перезагрузка |
| J2 | P1 | После обновления открыть портал | Страницы новые: файловая система стирается целиком. Настройки в EEPROM сохраняются |
| J3 | P1 | Отдать команду от просевших батареек, ниже 3300 мВ | Отказ, в следующем сеансе `ota_error` равен четырём. От USB, выше 4600 мВ, проверка пропускается |
| J4 | P1 | Битый адрес обновления | `ota_error` равен единице или тройке, уезжает в посылке и сбрасывается после публикации |
| J5 | P0 | Заводской сброс из портала | Возврат на приветствие, устройство снова не настроено. Плашка о перезагрузке ожидаема, см. B2 |

Подробности — [ota-and-reset.md](ota-and-reset.md).

## L. Быстрый регресс в симуляторе

Дешевле, чем на устройстве, и покрывает состояния, которых на стенде не
получить. Пульт — https://firmware-simulator.waterius.ru либо локальная сборка,
см. `simulator/README.md`.

| ID | P | Выставить с пульта | Открыть | Ожидаемо |
|---|---|---|---|---|
| L1 | P1 | версия attiny 40 | тревоги | Порог расхода и непрерывный расход скрыты, остановка расхода на месте, примечание про версию ниже 41. На стенде эту ветку не проверить |
| L2 | P1 | вес импульса «Авто» | тревоги | Поля порогов неактивны, подписи серые |
| L3 | P1 | тип входа «Выключен» | тревоги | Блок канала на месте, вместо полей примечание |
| L4 | P1 | всё настроено | тревоги | Ни одного примечания, все поля активны. Страница приезжает сразу правильной, поля не мигают при загрузке |
| L5 | P1 | снять связь по i2c | сохранить тип входа | «Ошибка связи с attiny» |
| L6 | P1 | внештатная перезагрузка ЕСП | главная | Плашка о перезагрузке |
| L7 | P1 | неверный пароль Wi-Fi | мастер | Ветка ошибки подключения |
| L8 | P2 | — | настройки Wi-Fi | Плашка ошибки не показывается, когда текста в ней нет |

Оговорка: симулятор — вторая реализация той же логики на JS. Его тесты ловят
структурные расхождения — новый плейсхолдер, адрес, поле формы, — но не поймают
разъехавшееся число или код ошибки. «В симуляторе работает» не заменяет
граничные проверки на железе.

## Что руками не проверяем

**Покрыто автотестами**, достаточно зелёного CI: арифметика показаний и
приростов, поправка периода пробуждения, разбор пользовательского ввода и
диапазонов, разбор адреса брокера, состояние страницы тревог как функция, маска
подтверждения, коды светодиодов, правила диагностических плашек, раскладка
настроек в EEPROM, таймеры портала, допустимые пары класса и единицы в Home
Assistant, детекция тревог в attiny по импульсам.

```bash
ESP8266/scripts/run_tests.sh && Attiny85/scripts/run_tests.sh
node ESP8266/scripts/test_strings.js
node simulator/test_simulator.js && node simulator/test_worker.js
```

**Известные расхождения** — не заводить как новые дефекты, они перечислены в
[known-gaps.md](known-gaps.md) и в разделе «Найденное по дороге»
`ESP8266/plan/tests_plan.md`.

**Вне стенда:** классика — другой набор пинов и светодиод на линии TX; attiny
старее 41 — только через симулятор, L1; тесты на живом железе из `Utils/tests/`
запускаются отдельно.
