# Показания: вес импульса, расчёт, приросты

Как импульсы превращаются в кубометры и киловатт-часы.

Расчёт живёт в чистом ядре `ESP8266/src/core/readings.cpp` и покрыт тестами
`ESP8266/test/test_readings`. Arduino-обёртка `ESP8266/src/config.cpp:calculate_values` только
логирует результат.

## Вес импульса

`sett.factor0` и `sett.factor1` означают разное в зависимости от типа ресурса:

- **вода, газ, тепло** — литров на импульс;
- **электричество** — импульсов на киловатт-час.

Два значения зарезервированы под специальные режимы (`ESP8266/src/core/types.h`):

| Значение | Константа | Смысл |
|---|---|---|
| 3 | `AUTO_IMPULSE_FACTOR` | Определить автоматически при настройке |
| 7 | `AS_COLD_CHANNEL` | Взять вес холодного канала |

Побочный эффект: счётчик с настоящим весом 3 или 7 литров на импульс задать невозможно —
значение будет истолковано как спецрежим. Это зафиксировано тестом
`AutoFactor.MagicValuesShadowRealFactors`, чтобы поведение не изменилось случайно.

Эти же значения служат признаком «устройство ещё не настроено»: `init_config` ставит
`factor0 = AS_COLD_CHANNEL` и `factor1 = AUTO_IMPULSE_FACTOR`, а портал по ним выбирает
стартовую страницу.

## Автоопределение

`ESP8266/src/core/readings.cpp:get_auto_factor` решает по числу импульсов, натикавших за время
настройки: три и меньше — счётчик на 10 л/имп, четыре и больше — на 1 л/имп. Порог —
`IMPULS_LIMIT_1` в `readings.h`.

Отсюда инструкция «спустите унитаз»: бачок это примерно 4 литра, то есть один импульс на
десятилитровом счётчике и четыре на литровом.

Определение идёт по **синему входу** (вход 1, холодная вода), поэтому в мастере настройки он
первый. Красный вход затем может унаследовать результат через `AS_COLD_CHANNEL`.

## Расчёт

`ESP8266/src/core/readings.cpp:calc_readings` для каждого канала с ненулевым `factor`:

```
вода/газ/тепло:  channel = start + (imp - imp_start) / 1000.0 * factor   // м³
                 delta   = (imp - imp_previous) * factor                  // литры
электричество:   channel = start + (imp - imp_start) / factor             // кВт·ч
                 delta   = (imp - imp_previous) / factor                  // кВт·ч
```

Асимметрия намеренная: показания уходят в кубометрах, а прирост — в литрах, потому что этого
ждёт сервер. Для электричества `delta` объявлена целочисленной, и дробная часть киловатт-часа
теряется — 1,5 кВт·ч уезжает как 1. Поведение зафиксировано тестом
`Readings.ElectroDeltaLosesFractionalKwh` как характеристика, а не как одобрение.

`imp_start` — импульсы в момент ввода показаний, `imp_previous` — импульсы в момент последней
успешной отправки. Первое даёт абсолютные показания, второе — прирост.

## Откат счётчика

Если `imp < imp_start`, значит attiny обнулился: заменили батарейки, сбросили, поставили
другой. Без обработки показания улетели бы в миллионы кубометров.

`calc_readings` в этом случае перезаписывает `imp_start` текущим значением и выставляет флаг
в `ReadingsStatus`. Точность теряется — расход между сбросом и обнаружением не учитывается, —
но показания остаются осмысленными.

Тот же откат считается расходом в режиме «только при расходе»
(`ESP8266/src/core/idle.cpp:consumption_detected`): любое изменение импульсов, включая
уменьшение, поднимает Wi-Fi.

## Прирост и потеря данных

`imp_previous` обновляется в `ESP8266/src/config.cpp:update_config`, то есть **только после
успешного сеанса**. Если отправка не удалась или Wi-Fi не поднялся, прирост продолжает
копиться и уедет одной дельтой в следующий раз.

Это и есть причина, по которой пропуск сеансов не теряет данные — ни при отсутствии
интернета, ни в режиме «только при расходе».

## Типы ресурса и типы входа

Не путать:

- **`CounterName`** (`cname`) — что считаем: холодная вода, горячая, электричество, газ,
  тепло в Гкал, питьевая вода, другое, тепло в кВт·ч. Определяет единицы, иконку и формулу.
- **`CounterType`** (`ctype`) — как считаем: дискретный, NAMUR, электронный, электронный с
  положительным импульсом, датчик Холла, выключен. Определяет алгоритм в attiny. Числа
  перечислены в `ESP8266/src/core/types.h` и обязаны совпадать с `Attiny85/src/counter.h`;
  проверка чужих значений — `ESP8266/src/core/input.cpp:is_valid_counter_type`.

`CounterName` хранится только в ЕСП. `CounterType` хранится в обоих: ЕСП шлёт его в attiny
командой `'C'` и держит копию для отображения.

Отсюда тонкость: команда из Home Assistant меняет тип входа в attiny и в живой копии
`runtime_data`, а payload собирается из снимка `data`, снятого в начале сеанса. Без переноса
значения наверх в HA возвращался бы старый тип и селектор отщёлкивал назад (#360). Перенос —
`ESP8266/src/core/readings.cpp:apply_counter_types`, вызывается из `main.cpp` сразу после
применения настроек. Копируются только типы: импульсы трогать нельзя, по ним уже посчитаны
отправленные дельты.

## Проверка ввода

`ESP8266/src/core/input.cpp:check_reading` требует, чтобы показания воды содержали
десятичный разделитель — точку или запятую (`core/input.cpp:has_decimal_separator`,
`core/input.cpp:parse_decimal` считает их равноправными). На шкале водяного счётчика
литры есть всегда, поэтому целое число в этом поле означает, что пользователь переписал
шкалу подряд: 123456 вместо 123.456. Ошибка возвращается отдельным кодом
`PARAM_ERR_NO_COMMA` — «похоже, забыта запятая».

Проверяется строка, а не разобранное число. По величине опечатку не отличить: 250000
бывает и забытой запятой в 250.000, и настоящей шкалой большого счётчика. Прежний
вариант правила (#353) стоял именно на величине — потолок 100 000 м³ — и отсекал
владельцев таких счётчиков вместе с опечатками.

Правило действует только для воды (`core/input.cpp:is_water_counter`): у электричества
целые кВт·ч — обычное дело, газ и тепло тоже не режем.

Показания записываются только при успешной проверке —
`ESP8266/src/portal/active_point_api.cpp:save_param` возвращает результат, и стартовые
импульсы сбрасываются лишь вместе с принятым значением.
