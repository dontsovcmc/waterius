# Симулятор портала

Онлайн-версия портала настройки Ватериуса: страницы открываются в браузере такими
же, какими их видит пользователь на устройстве, а «железо» — импульсы, кнопка,
attiny, Wi-Fi — имитируется с отдельной страницы-пульта.

Нужен для того, чтобы **глазами проверять страницы** — вёрстку, подписи, ошибки
полей, переходы мастера — не собирая прошивку и не поднимая точку доступа.

## Запуск локально

```shell
simulator/build.sh
cd simulator/dist && python3 -m http.server 8080
```

Открыть `http://localhost:8080/` — это пульт. На `localhost` service worker
работает без HTTPS, отдельной настройки не нужно.

Проверки:

```shell
node simulator/test_simulator.js   # плейсхолдеры, маршруты, поля форм, мастер настройки
node simulator/test_worker.js      # service worker целиком, в песочнице Node
node simulator/test_wizard_browser.js   # мастер и тревоги кликами в настоящем браузере
```

Первые две проверки логику и разметку разбирают в песочнице Node - браузер им
не нужен. Третья открывает страницы в Chromium и кликает по ним: она и только
она видит то, что видит пользователь - переходы, ошибки полей на экране,
упавший скрипт и органы управления пультом, которых нет без DOM. Браузер она берёт установленный, сама ничего не
качает:

```shell
npm install --prefix simulator     # playwright-core, без браузеров
npx playwright install chromium    # один раз, если браузера ещё нет
```

Без браузера проверка выходит с кодом 2 и говорит, чего не хватает: молчаливый
пропуск превратил бы её в вечнозелёную.

## Как устроено

Страницы из `ESP8266/data/` копируются сборкой в `dist/fw/` **побайтово** —
симулятор их не редактирует, иначе теряется весь смысл. В `ESP8266/data/` ничего
не добавляется: этот каталог целиком едет в образ LittleFS, где места нет.

Service worker перехватывает запросы и делает то же, что веб-сервер ЕСП:

| Запрос | Что происходит | Порт из |
|---|---|---|
| `/index.html`, `/wifi_settings.html`, … | берётся `fw/<файл>`, подставляются `%плейсхолдеры%` | `processor_main()`, `active_point.cpp` |
| `/input/0/setup.html` | берётся `fw/input_setup.html` с `input = 0` | таблица маршрутов, `active_point.cpp:501` |
| `/api/*` | обработчик, коды ошибок как в прошивке | `active_point_api.cpp` |
| `/static/*`, `/images/*` | отдаётся как есть | — |
| `/sim-api/*` | команды пульта | только симулятор |

Service worker понадобился потому, что `common.js` ходит между страницами через
`window.location`, то есть обычными переходами браузера: ни iframe, ни SPA-обёртка
их не перехватят.

### Штамп сборки

`build.sh` считает хэш всего, что уезжает на сайт, и подставляет его в `sw.js`
(`var BUILD`), в `?v=` у каждой библиотеки воркера и у скриптов пульта.

Без штампа симулятор разъезжается, причём молча. Браузер обновляет воркер, только
если изменились **байты самого `sw.js`**, а библиотеки из `importScripts` живут в
его кэше скриптов и переезжают вместе с ним. Правка в `processor.js` байты `sw.js`
не меняет — и у того, кто заходил раньше, новые страницы образа начинает
обслуживать логика прошлой сборки: неизвестное имя подстановки превращается в
пустую строку, страница выглядит рабочей и врёт.

Так и случилось после [#435](https://github.com/dontsovcmc/waterius/pull/435):
новая `alarms.html` приехала сразу (страницы образа воркер тянет с
`cache: 'no-store'`), а `%alarm_raised%` подставлял воркер прошлой сборки —
и блок снятия тревог висел на странице всегда.

### Состояние

Настройки, модель attiny и Wi-Fi лежат в **IndexedDB** этого браузера. Не в
cookies: воркер не видит заголовок `Cookie` — браузер его туда не отдаёт, — а
состояние нужно именно воркеру, это он отрисовывает страницы. Свойства те же:
ничего не уходит на сервер, у каждого браузера своя песочница, кнопка «Сброс к
заводским» чистит начисто.

### Что читается из прошивки

`gen_from_firmware.js` разбирает исходники и выдаёт таблицу: имена параметров из
`portal/resources.h` и `ha/resources.h`, поля `Settings` с длинами и значениями по
умолчанию, перечисления `CounterType` и `CounterName`, версию прошивки из
`platformio.ini`. Поэтому предел длины поля или новое умолчание не разъезжаются —
они не переписаны руками, а прочитаны.

## Чем отличается от устройства

- **Корень `/` — это пульт**, а главная портала на `/index.html`. Пульт нужен точкой
  входа, чтобы зарегистрировать service worker до первого перехода. По этой же
  причине сброс к заводским (`/api/reset` отвечает `redirect: "/"`) уводит на пульт.
- Показания никуда не отправляются: ни на waterius.ru, ни по MQTT, ни по HTTP.
- Сканирования сетей нет — список задаётся на пульте.
- Занятость LittleFS на странице «О программе» считается приблизительно, блоками
  по 4 КБ: точное число знает только собранный образ.
- Портал не выключается по таймеру 10 минут и не перестаёт отвечать после кнопки
  «Готово» — только помечает это на пульте.
- **Тревоги не детектируются, а задаются пультом.** Детекция живёт в attiny и считает
  импульсы часами — воспроизводить это в браузере нечем. Пульт даёт по галочке на бит
  (три на канал, имена битов берутся из прошивки), а всё, что после них, работает
  по-настоящему: плашки на главной, точечное снятие, кнопка на странице тревог и
  снятие при выключении режима «Я уехал». Галочки, а не список наборов, потому что
  тревоги складываются: две плашки с раздельным снятием иначе не проверить.

## Правило синхронизации

**Правка портала и правка симулятора едут одним PR.** Симулятор — вторая
реализация логики, на JS: подстановку значений, ответы `/api/*` и проверку полей
в браузере выполнить нечем, они переписаны с C++.

Тесты ловят структурные расхождения — новый плейсхолдер, новый адрес, новое поле
формы, непройденный мастер. Изменившееся число или ветку они не поймают: новый
предел длины, другой код ошибки, другой редирект. Это на дисциплине.

## Что уже нашли проверки

**Настроенный датчик протечки показывался как NAMUR.** `input_setup.html` предлагает
типы входа 5 и 6 (датчик протечки на замыкание и на размыкание, #202), прошивка их
сохраняла и отправляла в attiny, но `is_valid_counter_type()` в `core/input.cpp` про
них не знал: в его `switch` были только NAMUR, DISCRETE, ELECTRONIC, HALL,
ELECTRONIC_HIGH и NONE. Через эту функцию проходит `valid_counter_type()`
(`active_point.cpp`), который отрисовывает `%counter_type%`, — открыв страницу входа
заново, пользователь видел NAMUR, а сохранив её, терял настройку датчика.

След слияния: проверка приехала с диагностикой настройки (#283), типы входа — с
тревогами (#202), а `EXPECT_FALSE(is_valid_counter_type(5))` писался, когда типа 5 ещё
не существовало. Починено здесь же; в `test_input.cpp` добавлена проверка, что **каждый
пункт селектора** «Тип входа» функции известен.

Список известных типов симулятор снимает прямо со `switch`, поэтому такие расхождения
он повторяет, а не сглаживает: его дело — показывать то, что покажет устройство.

**Блок снятия тревог висел в портале всегда.** Не расхождение с прошивкой, а
доставка: см. «Штамп сборки» выше. Стоит помнить как класс — симулятор состоит из
двух половин, страниц образа и логики воркера, и версии у них обновлялись
по-разному.

## Публикация

Симулятор живёт на **https://firmware-simulator.waterius.ru** — публикует
`.github/workflows/simulator-deploy.yml`: пуш в `dev`, затрагивающий портал или
симулятор, гоняет проверки, собирает `dist/` и выкладывает на GitHub Pages. Поддомен
задан переменной `DOMAIN` в начале workflow.

Симулятору нужны две вещи: **корень домена** и **HTTPS**. Корень — потому что страницы
ссылаются на `/static/…` и `/images/…` абсолютными путями, а область видимости service
worker ограничена его каталогом. HTTPS — потому что вне `localhost` браузер не даст
зарегистрировать service worker, без которого не работает ничего.

Как это настроено — на случай, если понадобится повторить или перенести:

1. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
2. **DNS: CNAME** `firmware-simulator` → `dontsovcmc.github.io.` У зоны waterius.ru есть
   wildcard `*.waterius.ru` → `prod-02`, поэтому запись нужна именно явная: она
   перебивает wildcard.
3. **Settings → Pages → Custom domain**: `firmware-simulator.waterius.ru`. GitHub
   проверяет DNS в момент сохранения, так что порядок с шагом 2 не переставить.
4. Когда GitHub выпустит сертификат (минуты, изредка до часа) — **Enforce HTTPS** там же.
5. **Разрешить деплой с `dev`:** Settings → Environments → `github-pages` → Deployment
   branches. По умолчанию окружение пускает только ветку по умолчанию (`master`), а
   публикуемся мы с `dev`. Симптом — job падает за три секунды, не начав шагов.

Свой nginx подходит не хуже: `root .../simulator/dist;` на поддомене с сертификатом,
деплой чем удобно. Содержимое `dist/` — обычные файлы, бэкенда нет.
