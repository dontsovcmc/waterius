## 6e. Что нашёл первый живой прогон

Три поломки в самом стенде. Все три зеленели бы на симуляторе и молчали до тех пор,
пока не появится настоящее устройство.

- [x] 6e.1 Фильтр не резал ничего: правила заводились в списке `from_ap`, а исходящий
      трафик клиента проверяется по `to_ap` (`netif_hooks.c`: `ap_netif_input_hook` ->
      `ACL_TO_AP`). На этом стоят `internet_down`, `cloud_down`, `mqtt_down` - то есть
      G4, F2, F3, F4, D2b зеленели бы, ничего не проверяя. Проверено на живой паре:
      с правилом в `to_ap` счётчик `denied` растёт, клиент наружу не ходит
- [x] 6e.2 `blink_cause` обвинял конфиг в каждом сеансе: `Config succesfully loaded`
      печатается до `Startup mode:`, то есть в преамбуле, а причина искалась в тексте
      сеанса. Добавлен `Session.full_text` для фактов, печатаемых при загрузке
- [x] 6e.3 Схема посылки требовала полей, которых до 2.0.47 нет (`alarm_*`, `af/al/as`,
      `vac`, `sc`, `ack*`). Версии взяты из истории `json.cpp`. Схема разделена на базовую
      и добавленную с версии
- [x] 6e.4 `test_G4` помечен версией: причина `cloud` считается по статусам получателей,
      а 2.0.44 мигает единственным кодом - про конфиг
